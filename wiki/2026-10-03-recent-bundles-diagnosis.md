## 조사 결과

현재 localhost:8765의 캐시가 준비된 `/api/bundles`는 3회 44/34/45ms, 응답 2447바이트·15개 번들이다. Chromium 새 페이지에서는 API 73ms, 최근 5개 표시 확인 시점이 navigation 시작 후 162ms였다. 이 측정에서 지속적인 긴 지연은 재현되지 않았다.

별도 Python 프로세스에서 실제 같은 저장소를 읽고 프로세스 캐시를 비운 후 조회를 반복했다. 운영 서버의 캐시·데이터·상태는 건드리지 않았다. 디스크/OS 페이지 캐시는 비우지 않았으므로 완전히 차가운 디스크 측정은 아니다. 계측을 위해 JSON 읽기 횟수와 파일 크기를 세었다.

| 반복 | 캐시 비운 조회 | 이어진 조회 | JSON 파싱 파일 | JSON 용량 |
|---|---:|---:|---:|---:|
| 1 | 1.148초 | 0.030초 | 1834개 | 84.6MiB |
| 2 | 0.851초 | 0.029초 | 1834개 | 84.6MiB |
| 3 | 0.852초 | 0.034초 | 1834개 | 84.6MiB |

전체 15개 번들, 1208개 문서를 조사했다. 별도 cProfile 측정은 전체 1.324초 중 `_bundle_counts` 누적 1.125초, JSON 파싱·디코딩 0.792초였다. profiler 오버헤드 및 스레드 중첩 때문에 개별 시간을 단순 합산하지 않는다.

## 근본 원인과 동일 유형

1. 홈의 `api.listBundles()`는 전체 `/api/bundles`를 요청한 뒤 `state.bundles.slice(0, 5)`로 화면에서만 5개를 자른다. 서버의 limit·pagination이 없어 화면에 나오지 않는 번들까지 처리한다.
2. 서버 `list_bundles`는 모든 번들에서 공유 lifecycle 잠금과 DB 상태를 조회한 후 `_bundle_counts`를 호출한다. 이름·검수 상태는 DB에 있지만 문서/Golden/오류 건수는 파일에서 다시 집계한다. 특히 오류 건수는 모든 문서의 Golden·AO·Harness·ao_ui JSON을 읽고 파싱한다.
3. 집계·JSON 캐시는 워커 프로세스 메모리다. 재시작 또는 다른 워커의 첫 요청에서는 다시 채워야 한다. `_MEMO`는 4096개 키 도달 시 전체를 비우므로 이후 문서 탐색·편집·내보내기로 캐시가 많이 쌓이면 목록 집계도 다시 실행될 수 있다. 재시작 없는 운영 상황에서 실제 eviction 발생 여부는 이번 조사에서 계측하지 않았다.
4. 홈은 처음 빈 번들 상태를 표시하고 조회 실패를 빈 catch로 무시한다. 지연·오류 때 로딩/재시도 안내가 없어 현재 무엇을 기다리는지 알기 어렵다.

문제 유형은 가벼운 목록 조회가 전체 파일 콘텐츠 검사에 의존하고 최근/전체 목록에서 요청 범위를 서버로 전달하지 않는 구조다. 최근 목록뿐 아니라 전체 목록의 첫 조회, 업로드/삭제 후 목록 갱신, 캐시 초기화 후 목록에도 적용된다. 현재 측정상 응답 크기와 브라우저 DOM 렌더링은 주 병목이 아니다.

## 개선 방향

- 최근 목록은 서버에서 최신 5개를 먼저 선택한 뒤 그 번들만 처리한다. 전체 목록도 서버 검색·정렬·pagination으로 범위를 제한한다.
- 집계 결과를 DB에 저장하고 업로드·Golden 변경·검수 변경·삭제 시 갱신한다. 이관 시 초기 집계, 외부 파일 변경 시 재집계 정책까지 포함해야 오류 건수의 정확성을 유지한다.
- 집계 캐시를 파싱 캐시와 분리하면 전체 JSON 캐시 초기화로 집계까지 사라지는 영향을 줄일 수 있다. 단순 파일 수만 세는 변경으로 오류 건수를 누락하지 않는다.
- 홈에 조회 중 상태·실패 메시지·재시도 버튼을 표시한다.

이번 요청은 원인 조사이며 애플리케이션 코드·실행 서버는 변경하지 않았다. 수초 이상의 지연이 계속 발생하면 그 시점의 Network timing과 워커/DB 대기 상태를 추가 확인해야 한다. 현재 측정은 장시간 지연을 직접 재현한 결과가 아니다.
