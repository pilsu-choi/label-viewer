# 실문서 수준 합성 데이터셋 생성

## 1. 목표

**한 번 만들고 끝나는 작업이 아니다.** 필요할 때마다 같은 명령으로 다시 돌리고, 새 서식·새 오류 유형이 생기면 설정만 추가해 늘려 가는 **반복 가능한 생성 파이프라인**을 만든다(12장).

`datasets/{유형}_테스트셋`(7종, 총 854건)은 실문서지만 양이 적다. 이를 보완할 **합성 데이터셋**을 만든다.

완성 기준은 하나다. **실문서와 섞어 놓았을 때 사람이 구별하지 못해야 한다.**

- 인쇄·스캔·팩스·휴대폰 촬영의 질감이 실물과 같아야 한다.
- 표의 선, 칸 나눔, 글자 정렬, 병합 머리글이 실제 병원 서식과 같아야 한다.
- 숫자와 날짜가 서로 맞아야 한다(합계, 산식, 진료기간).
- 이미지마다 정답(라벨)이 같이 나와야 하고, 형식은 지금 쓰는 정답지와 같아야 한다.
- 실문서에서 드물게 나오는 까다로운 사례(엣지케이스)를 빠짐없이, 평가에 쓸 수 있을 만큼 충분히 담아야 한다(5-5).

## 3. 앞선 합성 샘플에서 배운 것 (반복 금지)

25장 샘플은 다음 때문에 "만든 티"가 났다. 이번에는 전부 피한다.

- 서식 5개, 항목명 15종, 기관 5곳, 글꼴 1종 → 다양성 부족
- 회전·원근·잘림·저해상도·필기·도장·여러 쪽 문서 없음
- "scan"이 밝기 조절과 잡음 추가 수준
- 단가 100원 단위, 횟수 1~3, 일수 1~5 → 실제 분포와 다름
- 가상 코드(SYN…) 사용 → 실제 EDI·KCD 코드가 아님
- 이미지에 없는 값까지 정답에 넣음
- Python API에서 잘못된 옵션이 오류 없이 기본값으로 처리됨

## 5. 만드는 방법

### 5-1. 전체 흐름

```
① 문서 내용 생성 (값·코드·금액·날짜, 서로 맞게)
② 서식에 채워 깨끗한 원본 렌더링 (HTML/CSS → 고해상도 이미지)
③ 출력 매체 질감 입히기 (인쇄 → 스캔/팩스/촬영/화면캡처)
④ 정답 저장 (이미지에 실제로 보이는 값만, 좌표 포함)
⑤ 자동 점검 + 실물 대비 품질 측정
```

**문서 전체를 이미지 생성 AI로 그리지 않는다.** 글자가 깨지고 정답과 어긋난다. 이미지 생성 AI는 쓰더라도 책상·바닥 같은 촬영 배경에만 쓴다.

### 5-2. 서식 (가장 중요)

실제 서식을 충실히 다시 만든다. 그럴듯한 표를 새로 디자인하지 않는다.

- **법정 서식**: 진료비 계산서·영수증, 약제비 계산서·영수증, 진료비 세부산정내역, 진단서 등은 법령 별지 서식이 있다(국가법령정보센터). 칸 배치·문구·주석 문단·하단 안내문까지 그대로 옮긴다.
- **병원별 변형**: 실문서를 보면 같은 법정 서식도 병원 전산(EMR) 제품마다 다르다. 원본 데이터셋을 훑어 **서식 계열 목록**을 먼저 만든다(유형별 최소 8~15개 계열, 세부내역서는 더 많이). 계열마다 열 순서, 열 이름 표기("코드 {수가코드}" 두 줄 표기 등), 선 굵기, 음영, 가로/세로 방향, 글꼴 크기가 다르다.
- **글꼴**: EMR 출력물에 흔한 굴림·돋움·바탕 계열을 쓰되 라이선스가 자유로운 대체 글꼴(백묵 굴림/돋움/바탕, 나눔, Noto Sans/Serif KR, 함초롬 등)을 쓴다. 한 문서 안에서도 제목·본문·숫자 글꼴이 다를 수 있다.
- **실물 디테일**: 문서 상단 출력 정보("[400216821943300/10783/11:31]"), 쪽 번호 "1/3", 팩스 수신 머리줄("2020-OCT-30 16:58 From: … Page:5/32"), 측면 수신 일시 도장, 빈칸의 "0" 인쇄, 체크칸 [V], 주민번호 뒷자리 `*******` 가림, 검은 사각형 가림, "원본대조필"·병원 직인(붉은 인주, 번짐·기울어짐), 볼펜 표시·밑줄, 형광펜, 손글씨 메모, 하단 용지 규격 문구("210mm×297mm(백상지 80g/㎡)").
- **여러 쪽**: 세부내역서는 2~10쪽, 표가 쪽을 넘어가며 이어진다(머리글 반복 여부도 계열별로 다름). 쪽마다 별도 이미지 또는 다중 페이지 TIFF로 낸다.
- **줄바꿈·넘침**: 긴 EDI명칭은 칸 안에서 두 줄로 접히거나 잘린다. 실제처럼 처리한다.

### 5-3. 내용 (값이 진짜 같아야 함)

- **코드**: EDI 수가코드·약품코드는 심평원 공개 수가표·약제 급여 목록에서, 병명은 KCD-8 공개 목록에서 가져온다. 코드와 명칭, 단가가 서로 맞아야 한다.
- **분포**: 실문서 정답지에서 행 수, 항목 구성, 단가·횟수·일수 범위(소수 횟수 0.5·1.33 등 포함), 진료기간 길이를 집계해 그 분포로 뽑는다. 같은 항목 반복, 소계 행, 빈칸, 0 인쇄도 실제 비율대로 넣는다.
- **산식**: `check_drafts.py`의 규칙을 반드시 만족한다.
  - 세부내역서: 총액 ≈ 단가 × 횟수 × 일수 × (1, 1.1, 1.15, 1.2, 1.25, 1.3 중 종별 가산)
  - 영수증: 항목 합 = 합계 행, 본인부담 100원 미만 끝수 처리
  - 본인부담·공단부담 비율은 요양기관 종별(의원·병원·종합병원·상급종합)과 입원/외래에 맞춘다.
- **날짜**: 사고일 ≤ 진료시작일 ≤ 진료종료일 ≤ 발행일. 연도는 실문서 범위(2019~2023 중심).
- **개인정보 (실제처럼, 그러나 실재하지 않게)**: 환자·의사 정보 칸을 비우거나 "홍길동" 같은 티 나는 값으로 채우지 않는다. 형식과 분포는 실제와 같고 실존 인물과 연결되지 않는 무작위 값을 넣는다.
  - 이름: 성씨 빈도(김·이·박…)와 출생 연대별 흔한 이름 음절 분포로 조합한다. 한자 병기·외국인 이름도 실문서 비율만큼 넣는다.
  - 주민등록번호: 앞 6자리는 생년월일, 7번째 자리는 성별·출생 세기(1·2 / 3·4)와 맞춘다. 뒷자리는 무작위로 하고 **마지막 검증 자리는 일부러 틀리게** 만든다. 실문서처럼 뒷자리 전체·일부 가림(`*******`, `1******`)을 실제 비율로 섞는다.
  - 생년월일·성별·나이: 주민번호와 맞추고, 병명과도 그럴듯하게 맞춘다(예: 노인성 질환에 20대 배제, 산부인과 병명은 여성).
  - 주소: 실제 시·도·시군구·도로명 체계를 쓰되 건물번호·상세주소는 무작위로 만든다. 실제 주소 목록에서 그대로 뽑지 않는다.
  - 연락처: `010-XXXX-XXXX`, 지역번호 형식만 맞춘 무작위 번호. 병원 전화번호도 가상.
  - 환자등록번호·차트번호·영수증번호·병실(예: `82병동(829)`)·의사 면허번호: 서식 계열별 자릿수·형식을 실문서에서 집계해 같은 형식의 무작위 값으로 만든다.
  - 의사명·병원명·사업자등록번호·요양기관번호: 가상 값(10장 참고). 사업자등록번호처럼 검증식이 있는 번호는 검증에 실패하게 만든다.
  - 한 문서 안에서, 그리고 묶음 문서끼리 같은 사람의 값은 일치해야 한다.
  - 값 생성은 시드로 재현되게 하고, 생성한 개인정보 목록은 `meta/`에만 둔다.
- **문서 묶음**: 한 환자·한 사고 기준으로 진단서·영수증·세부내역서를 묶어 만들면 값이 서로 맞아 더 실제 같다(선택 사항, 2단계 이후).

### 5-4. 질감

촬영 방식별로 실물을 관찰해 단계별로 쌓는다. 같은 설정 반복을 막기 위해 모든 강도는 범위 안에서 무작위로 뽑는다.

| 방식 | 입힐 것 |
|---|---|
| 인쇄 (공통) | 토너 농도 불균일, 글자 가장자리 번짐, 프린터 줄무늬, 약간의 확대·축소 |
| 스캔 | 기울기 ±2°, 종이 결·누런 기, 뒷면 비침, 접힌 자국, 스테이플·펀치 구멍, 가장자리 그림자, 150~300dpi, JPEG/PNG/TIFF |
| 팩스 | 1비트 흑백 200dpi(또는 200×100 비대칭), 디더링, 가로 끌림 줄·누락 줄, 글자 뭉개짐, 송수신 머리줄, 여러 번 복사·팩스된 흔적 |
| 사진 | 원근 왜곡, 책상·바닥 배경, 조명 기울기·그림자·반사, 종이 휨, 초점 흐림, 손떨림, 휴대폰 JPEG 압축, 화이트밸런스 틀어짐, 일부 잘림 |
| 화면캡처 | 모니터 촬영 시 모아레, 뷰어 UI 테두리, 확대 비율에 따른 계단 현상 |

해상도·파일 형식·색 모드·DPI 메타데이터도 실문서 분포를 따른다(실측 예: 1653×2338 1비트 200dpi TIFF, 2480×3508 300dpi, 72dpi 사진 JPEG 등).

### 5-5. 엣지케이스

5-3·5-4는 실제 분포를 따른다. 그대로 두면 드문 사례는 100장 중 한두 장도 나오지 않는다. 그래서 엣지케이스는 **목록으로 관리하고 최소 비율을 따로 정한다.**

- **목록**: `generator/edge_cases.yaml`에 사례마다 이름, 설명, 적용 유형, 만드는 방법(서식·내용·질감 중 어디서), 정답 처리 방법을 적는다. 새 사례는 이 파일에 한 줄 추가로 끝나야 한다(12-5).
- **최소 비율**: 기본 recipe는 장수의 30%를 엣지케이스 문서로 채운다. 한 문서에 최대 3개까지 겹친다. 목록의 각 사례는 해당 유형에서 최소 3장 이상 나와야 한다. 나머지 70%는 실제 분포를 그대로 따른다.
- **표시**: 어느 문서에 어떤 사례를 넣었는지 `meta/`와 `manifest.jsonl`에 `edge_cases: [...]`로 남긴다. 사례별로 따로 채점할 수 있게 하기 위해서다.
- **정답**: 엣지케이스라도 6장 규칙을 그대로 따른다. 보이지 않거나 읽을 수 없는 값은 정답에서 뺀다. 애매하게 보이는 값은 생성 값 대신 사람이 읽을 수 있는 값만 넣고, 판정이 안 되면 그 칸을 정답에서 뺀 뒤 `meta/`에 이유를 적는다.
- **지나침 금지**: 실문서에서 한 번도 보지 못한 극단적인 조합(사진 + 팩스 + 90° 회전 + 절반 잘림 등)은 만들지 않는다. 각 사례에는 실문서 근거(파일명 또는 관찰 메모)를 붙인다.

최소 목록(실문서·오추출 분석에서 확인한 것 위주로 시작하고, 1단계 분석에서 보완한다):

| 구분 | 사례 |
|---|---|
| 배치·촬영 | 90°/180° 회전, 기울기 5° 이상, 문서 일부 잘림(표 끝 행·오른쪽 열), 한 이미지에 두 쪽 또는 두 문서, 다른 문서가 겹쳐 찍힘, 심한 원근·휨, 저해상도(긴 변 1000px 미만), 팩스를 다시 팩스·복사한 흔적 |
| 표 구조 | 표가 쪽을 넘어감(머리글 반복 있음/없음), 쪽 끝에서 행이 둘로 나뉨, 병합 머리글·두 줄 머리글, 선 없는 표, 열 순서가 표준과 다름, 빈 열, 소계·중간합계 행, 합계 행 없음, 행 수 1행/50행 이상 |
| 값·글자 | 긴 EDI명칭 줄바꿈·잘림, 소수·음수(환불·취소) 금액, 0 인쇄와 빈칸 혼재, 천 단위 쉼표 없음/마침표 사용, 날짜 형식 혼재(`2021.03.05`·`21-3-5`·`2021년 3월 5일`), 같은 항목 반복, 진료기간 하루/1년 이상, 연도가 범위 밖(2018·2024) |

| 내용 | 영수증 외래/입원 둘 다 체크 또는 둘 다 비어 있음, 사고일 없음, 병명 여러 개(10개 이상)·병명 없음, 수술 없음, 진단서 소견만 있고 표 없음, 한자·영문 병명 병기 |

## 6. 정답 규칙

- **보이는 값만 정답이다.** 생성에 쓴 값이라도 가려지거나 잘리거나 인쇄되지 않았으면 정답에서 뺀다(가림·잘림 영역과 글자 상자를 비교해 자동 판정).
- 인쇄된 그대로 적는다. 계산해서 채우지 않는다. 소수는 그대로 둔다. 소계 행도 인쇄돼 있으면 행으로 넣는다.
- 0이 인쇄된 칸과 빈칸을 구분한다.
- 날짜는 `YYYYMMDD`, 체크칸은 `Y/N` 등 `check_drafts.py`의 형식을 따른다.
- 같은 정답을 세 가지로 낸다.
  1. `_draft/*.draft.json` — 기존 draft와 같은 구조
  2. `golden/*.answer.json` — `build_golden.py`로 변환한 결과(직접 만들지 않는다)
  3. `meta/*.json` — 시드, 서식 계열, 질감 설정값, 글자·셀·행 좌표(최종 이미지 픽셀 기준)

## 8. 품질 측정 (완료 판정)

| 항목 | 방법 | 기준 |
|---|---|---|
| 라벨 정합 | `check_drafts.py` 전체 실행, `build_golden.py` 변환 | 오류 0건 |
| 보이는 값 정합 | 정답 값마다 좌표가 이미지 안·가림 밖에 있는지 | 위반 0건 |
| 사람 판별 | 실문서 20장 + 합성 20장을 섞어 사용자에게 제시하는 검수 페이지 | 사람이 맞힌 비율 60% 이하 |
| 판별 모델 | 실문서 vs 합성 분류기(작은 CNN, 촬영 방식별)로 교차 검증 | AUC 0.75 이하, 높으면 분류기가 본 단서를 찾아 고친다 |
| 분포 거리 | 촬영 방식별 KID/FID, 해상도·밝기·잡음 통계 비교 | 보고서에 수치 기록, 단계별로 줄어들어야 함 |
| 엣지케이스 포함 | `manifest.jsonl`의 `edge_cases` 집계를 5-5 최소 비율과 비교 | 전체 비율·사례별 최소 장수 미달 0건 |
| OCR 난이도 | 로컬 OCR로 실문서·합성의 글자 오류율 분포 비교 | 두 분포가 비슷함(평균 차 보고) |

- 분류기가 쉽게 구별하면 Grad-CAM 등으로 어느 부분을 보고 구별했는지 확인하고 그 단서를 없앤다(글꼴, 여백, 잡음 모양 등). 기준을 낮춰 통과시키지 않는다.
- AWS 배포·하네스 호출은 하지 않는다. 하네스 채점이 필요하면 결과를 정리해 두고 사용자에게 알린다(AWS 테스트는 배포 담당 세션만 한다).

## 9. 진행 순서

0. **틀 먼저** — 12장의 recipe 실행 구조, 실행 폴더, 품질 게이트를 먼저 만들고 그 위에서 아래를 진행한다.
1. **실문서 분석** — 원본 데이터셋과 테스트셋을 집계해 서식 계열 목록, 값 분포, 촬영 방식별 질감 특징을 `generator/profile/`(기계용 통계)과 `profile/real-profile.md`(사람용 요약)로 정리한다. 이 집계도 명령 하나로 다시 돌릴 수 있게 만든다.
2. **검수용 3장 생성 → 사람 검수 대기** — 7종 각 3장(총 21장)만 만든다. 유형마다 3장은 서로 다른 촬영 방식(가능하면 스캔·팩스·사진 1장씩)과 다른 서식 계열로 고른다.
   - 3장 중 1장 이상은 5-5 엣지케이스를 넣고, 어떤 사례를 넣었는지 검수 묶음에 적는다.
   - 검수 묶음: `runs/{실행 폴더}/review/`에 원본 이미지, 정답을 이미지 위에 표시한 확인용 이미지(값·칸 위치), 같은 유형 실문서 1~2장(비교용), 자동 점검 결과(`check_drafts.py`·보이는 값 정합)를 모은다.
   - 검수 요청: `review/README.md`에 볼 위치와 확인 항목(질감이 실제 같은가 / 서식·표가 실제 같은가 / 값·개인정보가 자연스러운가 / 정답이 이미지와 맞는가)을 적고, 사용자에게 검수 묶음 경로와 함께 검수를 요청한다.
   - **요청한 뒤에는 작업을 멈추고 사용자 응답을 기다린다.** 응답 없이 장수를 늘리지 않는다.
   - 응답이 "수정"이면 지적 사항을 반영해 다시 3장씩 만들고 검수를 요청한다. "승인"이 나올 때까지 반복한다. 회차별 지적 사항과 반영 내용은 `review/feedback.md`와 `datasets/synthetics/wiki/`에 남긴다(10-1).
   - 승인은 유형별로 받을 수 있다. 승인된 유형부터 다음 단계로 넘어간다.
3. **유형별 100장 생성** — 승인된 유형만 유형별 100장(기본값, 사용자 지시로 조정)을 만든다. 5-5 최소 비율을 지킨다. 생성이 끝나면 8장 품질 측정과 사람 판별 검수 페이지(실문서 20장 + 합성 20장)를 만들어 사용자에게 알린다.
4. **최종 보고** — 8장 측정 결과, 서식 계열별·촬영 방식별 장수, 남은 한계.

여러 유형·서식 계열 작업은 서로 독립이므로 병렬로 진행한다.

## 10. 지켜야 할 것

- **개인정보**: 실문서의 이름·주민번호·주소·등록번호를 옮기지 않는다. 합성 개인정보는 5-3 규칙으로만 만든다. 실문서 이미지를 잘라 붙이지 않는다(질감 참고는 통계·관찰로만).
- **실존 기관 사칭 금지**: 병원명·사업자등록번호·요양기관번호·의사 면허번호·직인은 가상으로 만든다. 번호는 실제 검증식을 통과하지 않게 만든다. 실제 병원 로고·직인을 쓰지 않는다. 데이터는 OCR 학습·평가 전용이며 외부 반출하지 않는다.
- 공개 코드표(EDI·KCD)와 법정 서식 양식은 그대로 써도 된다.
- 생성 코드는 간결하게 유지한다. 같은 역할을 하는 함수·클래스를 중복으로 만들지 않는다.
- 작업 내역은 프로젝트 폴더의 `datasets/synthetics/wiki/`에 남긴다(10-1). 루트 `wiki/`에는 작업 시작·완료처럼 큰 단계만 한 줄씩 링크한다.

### 10-1. 작업 기록 (wiki)

처음 시작할 때 `datasets/synthetics/wiki/`를 만들고 `index.md`·`log.md`부터 둔다. 이후 모든 작업 내역을 여기에 Open Knowledge Format(OKF)으로 기록한다. 형식은 루트 `wiki/`와 같다.

- **파일 이름**: `{YYYY-MM-DD}-{주제}.md`처럼 날짜를 앞에 붙인다(예: `2026-10-04-real-profile.md`, `2026-10-05-review-round1.md`).
- **frontmatter**: 모든 문서 맨 위에 다섯 항목을 둔다. 더 이상 맞지 않는 문서는 지우지 않고 `status: deprecated`로 바꾼다.

  ```yaml
  ---
  type: guide | report | analysis | log | index   # 문서 성격
  title: 문서 제목
  description: 한 줄 요약
  tags: [synthetic, dataset, ...]
  status: active | deprecated
  ---
  ```

- **본문 첫머리**: 날짜·브랜치·워크트리를 적는다.

  ```
  날짜: 2026-10-04
  브랜치: feat/real-profile (generator 저장소)
  워크트리: .worktrees/real-profile
  ```

- **index.md**: 새 문서를 만들 때마다 링크와 한 줄 설명을 추가한다.
- **log.md**: 날짜별로 `### Creation`(새 문서)·`### Update`(기존 문서 수정) 항목을 남긴다. 무엇을 바꿨는지 한 문장으로 적는다.
- **무엇을 남기나**: 단계별 결과(실문서 분석, 검수 회차별 지적·반영, 100장 생성, 품질 측정), 실행 기록(실행 폴더·recipe·게이트 결과·사용처, 12-6), 결정 사항과 그 이유, 해결한 문제의 원인과 수정 범위.
- **언제**: 단계가 끝날 때마다, 그리고 사용자에게 검수·결정을 요청하기 직전에 기록한다. 몰아서 마지막에 쓰지 않는다.

## 12. 반복 가능한 구조

### 12-1. 원칙

- **설정으로 돌린다.** 무엇을 몇 장, 어떤 비율로 만들지는 코드가 아니라 recipe 파일에 적는다. 같은 recipe·같은 생성기 커밋·같은 시드 → 같은 결과.
- **실행은 쌓는다.** 실행마다 새 `runs/` 폴더를 만들고 이전 결과를 덮어쓰지 않는다. 학습·평가에 쓴 실행 폴더 이름을 기록하면 언제든 같은 데이터를 다시 찾을 수 있다.
- **생성기는 Git으로 관리한다.** `datasets/synthetics/generator`를 별도 Git 저장소로 만들고 gitlab에 올린다(`dev` 기준, 작업은 `.worktrees/<주제>` + `feat/` 브랜치, `AGENTS.md` 커밋 규칙). 이미지 결과물은 Git에 넣지 않고 `runs/`에 둔다.
- **품질 게이트를 통과한 실행만 쓴다.** 8장 측정을 실행 끝에 자동으로 돌리고 `reports/`에 통과/불통과를 남긴다. 불통과 실행은 지우지 않되 사용하지 않는다.

### 12-2. recipe 예시

```yaml
name: receipt-fax-heavy
seed: 20261003
profile: profile/2026-10-03          # 어느 시점 실문서 통계를 따를지
documents:
  - type: 진료비영수증
    count: 100
    families: all                    # 또는 [emr_a, emr_c]
    capture: real                    # 실문서 분포 그대로, 또는 {fax: 0.7, photo: 0.3}
  - type: 진료비세부내역서
    count: 100
    pages: [2, 6]
    emphasis: [long_edi_name, subtotal_rows]   # 표적 생성용 조건 (12-4)
edge_cases:                          # 5-5
  ratio: 0.3                         # 엣지케이스 문서 비율
  min_per_case: 3                    # 사례별 최소 장수
  max_per_doc: 3
  include: all                       # 또는 [rotate_90, page_split_row]
quality_gate: default                # 8장 기준
```

실행은 한 줄로 끝나야 한다.

```
python -m synth profile   --out profile/YYYY-MM-DD      # 실문서 통계 다시 집계
python -m synth run       recipes/receipt-fax-heavy.yaml # 생성 + 정답 + 품질 게이트
python -m synth report    runs/<실행 폴더>                # 보고서·사람 판별 검수 페이지
```

### 12-3. 고정 세트와 소모 세트

| 구분 | 용도 | 규칙 |
|---|---|---|
| 고정 평가 세트 | 하네스·Docraft 변경 전후 비교 | recipe·시드 고정, 버전 이름 붙여 보관(`synth-eval-v1`), 생성기가 바뀌어도 다시 만들지 않음. 새 버전은 `v2`로 따로 만든다 |
| 고정 엣지케이스 세트 | 사례별 약점 확인 | `synth-edge-v1`처럼 따로 보관, 5-5 목록의 사례마다 유형별 5장 이상, 사례별 점수를 따로 보고 |
| 소모 세트 | 학습·실험·특정 오류 재현 | 필요할 때마다 새 시드로 생성, 실행 폴더 이름만 기록 |

### 12-4. 반복 주기 (언제 다시 돌리나)

| 계기 | 할 일 |
|---|---|
| 고객사·원본 데이터셋에 새 실문서가 들어옴 | `synth profile` 재실행 → 분포·질감 차이 보고 → 새 profile로 recipe 갱신 |
| 처음 보는 서식 발견 | `templates/{유형}/{새 계열}/` 추가(HTML/CSS + 설명 yaml + 실문서 대조 스크린샷) → 해당 계열만 3장 생성 → 사람 검수 요청·대기(9장 2단계와 같은 절차) → 승인 후 기본 recipe에 포함 |
| 하네스 오추출 분석에서 오류 패턴 발견 (예: 긴 EDI명칭 줄바꿈, 팩스 소수점 뭉개짐, 쪽 넘김 표) | 패턴을 `emphasis` 조건으로 추가하고 그 조건을 많이 담은 표적 세트 생성 → 수정 전후 비교에 사용 |
| 판별 모델이 새 "만든 티" 단서를 찾음 | 단서를 없애는 수정을 생성기에 넣고 고정 평가 세트는 새 버전으로 |
| 정답 정책 변경 (예: 소계 행·인쇄분만) | 정답 생성 규칙을 바꾸고 `check_drafts.py`·`build_golden.py`와 함께 맞춘 뒤 재생성 |

### 12-5. 확장 방법이 정해져 있어야 한다

- 새 문서 유형·서식 계열·질감 단계는 정해진 자리에 파일 하나(또는 폴더 하나)를 추가하는 것으로 끝나야 한다. 생성기 본체 코드를 고치지 않는다.
- `generator/README.md`에 "새 서식 계열 추가하기", "새 질감 단계 추가하기", "새 recipe 만들기"를 각각 체크리스트로 적는다.
- 생성기 테스트: 같은 시드 재현, 잘못된 recipe 값 거부, 계열마다 1장 생성 후 `check_drafts.py` 통과, 보이는 값 정합. 생성기를 바꿀 때마다 돌린다.
