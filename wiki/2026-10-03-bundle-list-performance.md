## 원인과 범위

[원인 조사](2026-10-03-recent-bundles-diagnosis.md)에서 홈 최근 5개가 전체 15개 번들·1208개 문서를 조사하고, 프로세스 캐시가 없으면 JSON 1834개·84.6MiB를 읽는 구조를 확인했다. 같은 저장소에서 캐시를 비운 조회는 1.148/0.851/0.852초, 다음 조회는 약 30ms였다. 문제 유형은 작은 목록 요청이 전체 파일 콘텐츠 검사와 프로세스 메모리 캐시에 의존하는 구조다. 최근 목록, 전체 목록, 재시작, 검수 변경, 외부 파일 수정에 같은 유형의 원인이 영향을 준다.

## 변경

- 홈은 `/api/bundles?limit=5`를 요청한다. 서버가 최신 5개를 먼저 선택하고 해당 범위만 집계한다.
- 전체 목록은 `/api/bundles/page`에서 검색·정렬·페이지 범위를 정한 뒤 선택된 번들만 집계한다. 전체 수·검색 결과 수·실제 페이지를 함께 반환하며 초과 페이지는 마지막 페이지로 맞춘다. 기존 매개변수 없는 `/api/bundles`의 배열 계약은 유지한다.
- PostgreSQL에 `bundle_summaries`를 추가해 파일 집계를 보관한다. namespace별로 격리하고 번들 삭제 시 함께 삭제한다. 저장된 집계는 원본 콘텐츠가 아니라 재생성 가능한 메타데이터다.
- 파일 이름과 stat 정보를 비교해 외부 교체·추가·삭제·같은 크기 인플레이스 변경도 확인한다. JSON 파싱 결과는 변경 문서만 다시 계산한다. 검수 상태는 현재 DB 상태와 실제 문서 ID로 계산하므로 JSON 집계를 무효화하지 않는다.
- 파일 변경 전후를 확인해 변경 중인 결과를 영속 캐시에 게시하지 않는다. 기존 JSON 파싱 캐시와 목록 집계 캐시를 분리한다.
- 홈은 조회 중·실패·재시도를 표시한다. 전체 목록 검색을 200ms debounce하고 늦은 응답과 화면 종료 후 응답을 무시한다.

## API와 정렬

`GET /api/bundles?limit=5`는 최신순 배열이며 limit 범위는 1~100이다.

`GET /api/bundles/page?query=&sort=newest&page=1&page_size=50`는 `{items,total,filtered_total,page,page_size}`다. 이름/ID 검색의 `%`, `_`는 와일드카드로 확장하지 않는다. sort는 newest/oldest/name, page는 1 이상, page_size는 1~100이다. 이름 정렬은 대소문자를 무시한 사전순이며 동률이면 실제 이름·ID로 순서를 확정한다. 이전 브라우저 locale의 숫자 자연 정렬과는 차이가 있을 수 있다.

## 검증·실측

동일 실제 저장소를 읽는 별도 프로세스에서 DB 집계 준비 후 메모리 캐시를 비워 반복 측정했다. PostgreSQL 연결 풀은 초기화했고 OS 디스크 캐시는 비우지 않았다. 기존 조사와 비교할 때 첫 연결 준비 비용을 제외한 반복값을 기준으로 한다.

| 범위 | 1회 | 2회 | 3회 | 중앙값 |
|---|---:|---:|---:|---:|
| 이전 홈 요청: 전체 15개 조사 | 1.148초 | 0.851초 | 0.852초 | 0.852초 |
| 개선 홈 요청: 최근 5개 | 0.0221초 | 0.0184초 | 0.0204초 | 0.0204초 |
| 개선 전체 15개 | 0.0520초 | 0.0472초 | 0.0452초 | 0.0472초 |

프로세스 캐시가 없는 홈 요청 기준 약 97.6% 감소했고, 범위를 같게 둔 전체 조회도 약 94.5% 감소했다. 개선판 반복 조회는 JSON 파싱 **0회**, DB 요약 재저장 **0회**였다. 이전 이미 준비된 API는 25~53ms로 빨랐으며, 이번 개선의 큰 이점은 재시작·캐시 초기화 후 전체 JSON 재검사 방지다. 전체 조회는 외부 파일의 인플레이스 수정까지 감지하는 stat 검사 때문에 기존 메모리 캐시 hit보다 추가 비용이 있을 수 있다.

별도 18965 앱의 HTTP 최근 5개 응답은 24.8/22.7/24.3ms, 전체 페이지 응답은 61.3/58.6/60.3ms였다. 최초 집계 후 새 프로세스에서도 기존 API의 15개 번들 요약과 문서·Golden·검수·오류 건수가 모두 동일했다.

- PostgreSQL 포함 전체 회귀 **176 passed**, 31.72초. 이후 버전 변경 재검사·검수 변경 무파싱·삭제 cascade 회귀를 추가하여 목록 성능 관련 7개 테스트가 모두 통과했다. 전체 고유 테스트는 178개다.
- 파일 모드와 PostgreSQL에서 최근 범위·필터·정렬·페이지 clamp, 동일 크기/mtime 복원 JSON 수정, 변경 문서만 파싱, 집계 버전 갱신, 검수 상태 변경 후 파싱/쓰기 없음·삭제 cascade 확인.
- Chromium의 최근 5개 요청·loading/error/retry, 검색 debounce·늦은 응답 무시·정렬·page_size·서버 페이지 clamp·화면 종료 확인. 기존 frontend/export 회귀도 통과.

## 범위와 한계

파일 stat 확인은 남아 있으며 선택 범위의 파일 개수에 비례한다. 처음 보는 번들이나 바뀐 문서에는 JSON 검사가 필요하다. 파일·DB 사이의 강제 종료 원자성 및 백업 조건은 [기존 점검 기록](2026-10-03-postgres-performance-audit.md)을 따른다. 이 캐시는 OCR·Golden 콘텐츠를 수정하지 않으며 기존 오류 집계 의미를 유지한다.
